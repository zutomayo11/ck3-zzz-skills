# Mod 体积与无损整理

## Pack1、Pack2 普通 DDS 有损压缩（1.2.0）

沿用 Miyabi 的 DirectXTex 流程，先用 texdiag 核实 170 张 DDS 均为 BGRA8，再按实际用途分类。Pack1 选择 55 张颜色、43 张法线；Pack2 选择 25 张颜色、17 张法线；其余 9 张面部动画和 21 张辅助数据图保留。普通面部 diffuse 属于颜色图，不能与 face_animation 数据图混淆。

颜色优先 BC7，任何原本全不透明的 mip 在压缩后出现非 255 Alpha 都回退 BC3；结果为 BC7 32 张、BC3 108 张（其中法线 60 张）。原法线由生成器写为 RRxG，G=X、A=反向Y、B=0；按 shader 的 G/A 解码验证，不能直接 BC5 丢掉 Alpha。逐级读取全部 1610 层 mip，保持宽高与 mip 数，验证不透明 Alpha 和法线蓝通道；不能只检查最高层。

| 正式包 | 压缩前 MiB | 压缩后 MiB | 减少 MiB |
|---|---:|---:|---:|
| Pack1 妄想天使 | 2863.73 | 1826.95 | 1036.78（36.20%） |
| Pack2 维多利亚家政 | 1990.61 | 1541.60 | 449.00（22.56%） |

正式输入为 `sources/faction_texture_compression/` 的 `report.json`、`baseline.json` 和 `candidates/`，另存 texdiag 前后结果。构建收尾调用 `scripts/apply_faction_texture_compression.py`，全量预检 140 个源及候选哈希后才复制；重复应用跳过，源改变须在保留历史记录的前提下重新生成审核，不能覆盖旧 baseline 来绕过检查。准备工具为 `scripts/prepare_faction_texture_compression.py`；已应用后再次运行准备工具会因基线变化停止，应直接复用正式候选。不要删除本目录，也不要误删 Pack3 独立的 `experiments/miyabi_texture_compression/` 依赖。

正式应用记录在 `reports/faction_texture_compression_1_2_0.json`，备份在 `backups/before_1.2.0_texture_compression_20260930_011837/`。三个包 4831 文件的变化集合严格等于 140 张目标 DDS 和 3 个版本描述文件；包括 4095 个 `.anim` 在内的其余 4688 文件哈希不变。未启动游戏、未上传工坊；有损颜色及法线效果仍需实际加载复测。

## 星见雅普通 DDS 有损压缩（1.1.0）

正式 Pack3 的 21 张普通贴图来自 Microsoft DirectXTex 试验：颜色优先 BC7，四张要求全不透明 Alpha 的颜色图用 BC3；七张 RRxG 法线用 BC3，以保留 CK3 `UnpackRRxGNormal` 实际读取的 G/A 通道。不要对这些法线直接选 BC5，也不要依据文件名把 face_animation、regions、properties、LUT、MatCap 和中性占位图一并压缩。Pack3 从 568.12 MiB 降至约 349.12 MiB（减少约 219 MiB、38.55%）；这属于有损纹理格式变化，不是无损去重或 NTFS 透明压缩。

审核数据、texdiag 前后格式、逐图哈希和候选 DDS 位于工程 `experiments/miyabi_texture_compression/`。正式构建的 `apply_miyabi_texture_compression` 依赖其中 `report.json` 和 `BC7_UNORM/`、`BC3_UNORM/`；后续清理实验目录前必须迁移这些正式输入。重建时源/候选哈希不符应停止并重新测试。240 层 mip 已离线回读，丝袜纯黑阈值边界有少量有损像素变化；画质、BC7 加载与 shader 效果仍需游戏内确认，不能凭离线哈希断言完全正常。

先分别统计正式输出、作者工程、备份、预览、临时导出。只有输出目录才是实际 Mod 包体积；工程备份留在磁盘不代表进入了游戏包。使用实际字节数，注明 MB 或 MiB，不把预估当实测。

主要来源通常是面部顶点动画 DDS、高清贴图、重复服装资源与原生骨骼采样。原生表情图集按“面部顶点 × 每顶点像素 × 总帧数”增长，每帧是成千顶点的数据；身体 anim 主要保存骨骼 T/Q/S，二者不是同一种逐帧存储。删帧、降 fps、量化、降低纹理分辨率或有损压缩属于质量取舍，不应冒充无损优化。

正式工具 `scripts/optimize_resources.py` 已实现：

- 对同目录字节完全相同的 DDS 共用引用，同步 asset、二进制 mesh 材质、shader 和报告。内容/尺寸相似不等于字节相同，独立逆绑定或不同表情布局也不能共用。
- 表情图集裁去空白列，保持每个有效像素、帧数、范围和原 mesh UV。shader 用 encoded_uv_width 换算到实际图集宽度；高度、单 mip 和时钟范围按报告生成。不能直接改宽度而忘 UV 解码。
- 先全包搜索 asset、mesh、shader/include 和脚本引用，再将确认无引用生成资源移到备份。包括旧 include 在内的潜在引用未消除前不要删。小型眼色 LUT 仍用于源颜色验证。
- 重建内容散列 include，更新报告，并验证优化前后骨动画不变、网格几何/骨架/权重/UV 不变。重复运行应不改变资源结果。

眨眼不需要为每段动作生成整张逐帧表情图集。同一皮肤的所有动作共用该皮肤的眼睑形态，动作只存小时钟曲线；多皮肤可以各存几十行、共用一张 DDS，用材质宏选择行区间。旧空白行不足时只增加必要的64行对齐高度，原有效数据保留。本轮千夏三套独立眨眼额外占约1.62MB图集，避免三份完整 DDS。原独立兼容补丁新增约183 MB是完整 DDS 覆盖副本的首次开销，不是每段眨眼的成本。合并到主包后直接扩展主包已有图集。

比较动画大小时分开统计新增动作本体、名称字符串变化和眨眼采样。当前逐帧动态时钟保留源 fps；只有确认格式/引擎支持时才考虑稀疏采样。身体恒定通道可仅存参考值，但必须逐帧回读验证压缩前后姿态，不修改原生待机和表情来源。

## NTFS 本地无损压缩与备份清理

0.16.2使用Windows自带 `compact.exe /C /S:<已解析的绝对目录> /I /Q` 对本地资源目录透明压缩。文件名、文件长度、内容哈希不变；无需改变模型、贴图、材质或动画格式。必须区分文件内容大小、NTFS压缩存储字节和分发包大小，不能宣称压缩后逻辑Mod包也变小。`scripts/audit_storage.py` 记录GetCompressedFileSizeW和每文件SHA256；压缩前后验证所有基线内容不变。源工程写入新内容时系统仍透明处理；仅文件系统存储压缩，不是降低纹理分辨率或采样率。

删除旧备份必须按版本元组比较，0.10不能当作小数0.1；检查绝对目录位于工程backups且无重解析点。用户指定删除0.10之前时，只清理明确0.0–0.9目录，保留0.10及后续验证依赖。移入回收站只能称为移出工程，实际磁盘空间要清空回收站后才释放，不把回收站字节计入压缩释放量。历史0.1对比预览脚本依赖已清理的旧备份，仅供旧版本追溯，不属于当前构建链。
